# Библиотека в системе контроля версий

Каталог компонентов живёт в SQLite. Для одного человека это удобно: один файл,
переносится копированием. Для отдела — нет: двоичный файл нельзя ни слить, ни
посмотреть в pull request, ни разложить по веткам.

Поэтому у библиотеки есть **текстовое зеркало** — папка обычных файлов,
которую и держат в git.

---

## Как это устроено

```
<папка репозитория>/
    library.tsv                 оглавление: по строке на компонент
    components/<имя>.json       сам компонент, по файлу на штуку
    models/                     3D-модели (по желанию)
    .gitattributes
```

`library.tsv` читается глазами и в diff показывает суть: что добавилось, у
кого сменился парт-номер. `components/*.json` — полное описание компонента:
символ, выводы, посадка, параметры.

Главное свойство — **устойчивость**: одна и та же библиотека даёт байт в байт
одинаковые файлы. Ключи отсортированы, отступ фиксированный, только LF,
никаких дат внутри. Без этого каждая выгрузка была бы diff на всю библиотеку,
и ревью потеряло бы смысл.

Слияние идёт по `uid` — он не меняется за всю жизнь компонента, а имя
поменяться может.

---

## Настройка

**Настройки → Библиотека → «Папка для git»**. Пусто — будет `library-git`
рядом с каталогом.

Второй флажок, **«выкладывать в репозиторий 3D-модели»**, по умолчанию снят.
STEP текстовый, git его переваривает, но библиотека на сотню корпусов — это
сотни мегабайт в истории. Обычно модели держат отдельно.

## Кнопка «Репозиторий ▾»

| Команда | Что делает |
|---|---|
| **Выложить библиотеку в папку** | записывает текущее состояние каталога. Меняет только те файлы, что действительно изменились |
| **Что изменилось** | сравнение каталога с папкой: что только у нас, что только в папке, что расходится |
| **Забрать новое из папки** | добавляет в каталог компоненты, которых у нас нет. Существующие не трогает |
| **Взять версию из репозитория** | заменяет и существующие. Локальные правки этих компонентов пропадут (`Ctrl+Z` вернёт) |
| **Синхронизировать** | забрать новое и выложить своё за один раз |
| **Открыть папку** | просто открывает её в проводнике |

## Обычный день

```bat
git pull
```

→ **«Забрать новое из папки»** в программе

→ работаете как обычно

→ **«Синхронизировать»**

```bat
git add -A
git commit -m "добавил STM32G431 и разъём USB-C"
git push
```

## Расхождения

Если один и тот же компонент правили и вы, и коллега, программа **не будет
решать за вас**. «Синхронизировать» выложит вашу версию и покажет список
расхождений:

```
Расходятся с репозиторием (выложена НАША версия):
  STM32F103C8T6
  USB_C_Receptacle
```

Дальше вы решаете: оставить своё или взять чужое кнопкой «Взять версию из
репозитория». Молча затирать чужую работу хуже, чем спросить.

Если расхождений много и разбираться в них лень, обычный git-путь тоже
работает: посмотреть `git diff` по конкретному `components/<имя>.json` и
решить по содержимому.

---

## Между своими машинами

Тот же механизм годится без всякого git: положите папку-зеркало в облачную
папку (Яндекс.Диск, OneDrive, что угодно) и укажите её в настройках на обеих
машинах. На одной «Синхронизировать», на другой «Забрать новое из папки».

Конфликты в этом случае разбираются так же вручную — автоматического слияния
по времени правки пока нет.

---

## Что НЕ надо коммитить

Всё это уже перечислено в `.gitignore` проекта, но если заводите отдельный
репозиторий под библиотеку — имейте в виду:

- `catalog.sqlite` — двоичный, сливать нечем; его роль выполняет
  `components/*.json`;
- `library\` с готовыми `.SchLib` / `.PcbLib` — это результат сборки, он
  воспроизводится за минуту;
- `jobs\`, `backups\`, `cache\` — рабочий мусор;
- `models\`, если не включили их явно.
